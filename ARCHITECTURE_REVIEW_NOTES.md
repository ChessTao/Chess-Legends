# Архитектурные замечания по онлайн-версии

Дата проверки: 2026-05-28.

Статус выполнения: пункты 1-5 закрыты в коде 2026-05-28. Ниже оставлены исходные требования как чек-лист для повторной проверки перед деплоем.

## Срочно перед публичным тестом

1. **Не раскрывать приватные комнаты в публичном списке**

   Сейчас публичный endpoint списка комнат должен отдавать только открытые комнаты. Приватные комнаты, их `code` и служебные поля нельзя показывать всем клиентам.

   Что сделать:
   - фильтровать `/api/online/rooms` по `!room.isPrivate`;
   - в `serializeRoom()` отдавать `code` только участнику комнаты;
   - проверить, что приватную комнату можно найти только по коду и паролю.

2. **Сбрасывать публичные комнаты после завершения партии**

   Публичная комната не должна навсегда оставаться `finished` или занятой после матча. Если оба игрока не нажали выход, комната все равно должна вернуться в состояние ожидания.

   Что сделать:
   - добавить reset публичной комнаты после `finishedAt`;
   - либо очищать finished-комнату при следующем запросе списка комнат;
   - сохранить результат матча до reset.

3. **Не хранить пароли приватных комнат открытым текстом**

   Пароль приватной комнаты сейчас не должен попадать в `.runtime/online-rooms.json` как plain text.

   Что сделать:
   - хранить `passwordHash` и `passwordSalt`;
   - сравнивать пароль через ту же схему, что используется для профилей;
   - не отдавать пароль/хеш клиенту.

## Следующий слой надежности

4. **Добавить срок жизни серверных сессий**

   Cookie имеет `Max-Age`, но runtime-хранилище сессий тоже должно знать срок жизни токена.

   Что сделать:
   - сохранять `createdAt` и `expiresAt` в `.runtime/sessions.json`;
   - очищать просроченные сессии при старте и во время запросов;
   - добавить `/api/logout`, который удаляет серверную сессию и сбрасывает cookie.

5. **Сделать восстановление онлайн-партии на клиенте устойчивее**

   Сейчас при refresh клиент сначала уводит состояние в меню, а потом пробует восстановить матч. Если запрос восстановления временно упал, следующая автопопытка может потеряться.

   Что сделать:
   - не перезаписывать `screen: onlineGame` до результата `resumeActive()`;
   - или хранить отдельный флаг `pendingOnlineResume`;
   - показывать понятное состояние ожидания восстановления, а не молча возвращать в меню.

## Остаточные архитектурные риски

- REST + polling годится для MVP, но WebSocket все еще желателен для настоящего онлайн-матча.
- JSON runtime-хранилище достаточно для первого закрытого теста, но для публичного доступа лучше перейти на SQLite.
- Нужно добавить сетевые тесты: приватная комната, вход вторым игроком, пара ходов, завершение матча, обновление рейтинга, refresh/reconnect.
- Перед деплоем нужны backup runtime-данных и проверка поведения при рестарте сервера.
