# Переход на БАЗУ ДАННЫХ

Решение обновлено: для бесплатного онлайн-размещения выбираем PostgreSQL и Docker-контейнеры. Это позволяет не платить за Render persistent disk и не хранить живые данные игры в `.runtime` на временной файловой системе.

Для первого закрытого теста входная страница будет размещена на `aveskulov.com` в скрытом разделе без ссылки с сайта и с `noindex`. Серверная часть и PostgreSQL могут жить отдельно, если текущий хостинг `aveskulov.com` не поддерживает Node.js/Docker/PostgreSQL.

Сейчас сервер хранит runtime-данные в JSON-файлах:

```text
.runtime/profiles.json
.runtime/sessions.json
.runtime/online-rooms.json
.runtime/server-errors.log
```

Раньше план был сначала вывести игру через persistent disk/volume, а базу данных отложить. Теперь путь меняется: `.runtime` оставляем как временный локальный fallback, а для онлайн-версии готовим PostgreSQL.

## Чем база данных отличается от persistent disk

Persistent disk сохраняет файлы как файлы:

```text
записать профиль -> открыть profiles.json -> изменить JSON -> сохранить файл
```

База данных хранит данные как структурированные записи:

```text
записать профиль -> INSERT/UPDATE в таблицу users
получить рейтинг -> SELECT из таблицы results
создать комнату -> INSERT в таблицу rooms
обновить матч -> UPDATE в таблицу matches
```

Примерные таблицы для будущего этапа:

- `users`
- `sessions`
- `rooms`
- `matches`
- `leaderboard_results`
- `password_reset_tokens`

## Зачем переходить на базу данных

База данных лучше подходит для долгосрочной онлайн-версии:

- надежнее работает при многих игроках;
- проще делать поиск, фильтрацию и доску лидеров;
- проще добавить восстановление пароля через email;
- проще делать админку и статистику;
- проще переносить данные между серверами;
- проще делать резервные копии и восстановление.

## Что придется перепроверить

При переходе на базу данных нужно заново проверить почти весь сценарий игры, потому что меняется слой хранения данных.

Обязательно перепроверить:

- регистрацию игрока;
- вход по паролю;
- сохранение профиля;
- сессию после обновления страницы;
- одиночные результаты;
- матчевую статистику;
- доску лидеров;
- онлайн-комнаты;
- приглашения;
- завершение матча;
- восстановление после перезапуска сервера;
- резервные копии;
- поведение при двух игроках одновременно.

Сама шахматная механика, карточки, правила и интерфейс могут остаться почти без изменений. Но все места, где игра читает или записывает данные игрока, нужно будет проверить заново.

## Рекомендуемый порядок

1. Подготовить Docker Compose для локального запуска `app + postgres`.
2. Добавить серверный слой хранения: JSON fallback и PostgreSQL при наличии `DATABASE_URL`.
3. Перенести профили и сессии в PostgreSQL.
4. Перенести онлайн-комнаты в PostgreSQL.
5. Прогнать полный smoke/e2e-сценарий локально.
6. Разместить скрытую страницу на `aveskulov.com` без ссылки и с `noindex`.
7. Разместить Node-приложение и PostgreSQL на бесплатных сервисах или на VPS, если у `aveskulov.com` есть Docker-доступ.
8. Прогнать `online-smoke` против публичного URL.
9. Дать ссылку 2-5 участникам закрытого теста.

Так мы убираем зависимость от платного persistent disk и заранее строим схему, которую потом проще расширять до нормальной публичной версии.
