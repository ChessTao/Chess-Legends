# Переход на БАЗУ ДАННЫХ

Переход на базу данных - это отдельный технический этап после первого онлайн-запуска.

Сейчас сервер хранит runtime-данные в JSON-файлах:

```text
.runtime/profiles.json
.runtime/sessions.json
.runtime/online-rooms.json
.runtime/server-errors.log
```

Для первого детского теста эти файлы можно хранить на persistent disk/volume хостинга. Это позволяет быстрее вывести игру в онлайн без большой переделки серверной логики.

## Чем база данных отличается от persistent disk

Persistent disk сохраняет файлы как файлы:

```text
записать профиль -> открыть profiles.json -> изменить JSON -> сохранить файл
```

База данных хранит данные как структурированные записи:

```text
записать профиль -> INSERT/UPDATE в таблицу users
получить рейтинг -> SELECT из таблицы results
создать комнату -> INSERT в таблицу rooms
обновить матч -> UPDATE в таблицу matches
```

Примерные таблицы для будущего этапа:

- `users`
- `sessions`
- `rooms`
- `matches`
- `leaderboard_results`
- `password_reset_tokens`

## Зачем переходить на базу данных

База данных лучше подходит для долгосрочной онлайн-версии:

- надежнее работает при многих игроках;
- проще делать поиск, фильтрацию и доску лидеров;
- проще добавить восстановление пароля через email;
- проще делать админку и статистику;
- проще переносить данные между серверами;
- проще делать резервные копии и восстановление.

## Что придется перепроверить

При переходе на базу данных нужно заново проверить почти весь сценарий игры, потому что меняется слой хранения данных.

Обязательно перепроверить:

- регистрацию игрока;
- вход по паролю;
- сохранение профиля;
- сессию после обновления страницы;
- одиночные результаты;
- матчевую статистику;
- доску лидеров;
- онлайн-комнаты;
- приглашения;
- завершение матча;
- восстановление после перезапуска сервера;
- резервные копии;
- поведение при двух игроках одновременно.

Сама шахматная механика, карточки, правила и интерфейс могут остаться почти без изменений. Но все места, где игра читает или записывает данные игрока, нужно будет проверить заново.

## Рекомендуемый порядок

1. Сначала вывести текущую версию онлайн через Node.js-хостинг и persistent disk.
2. Дать детям протестировать игру.
3. Собрать реальные замечания по игровому процессу.
4. После этого отдельным этапом перенести runtime-данные в базу данных.
5. Заново пройти полный smoke/e2e-сценарий.

Так мы не смешиваем два больших риска в один этап: деплой и смену хранилища.
