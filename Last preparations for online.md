# Last preparations for online

Перед закрытым онлайн-тестом цель не "дописать все", а довести MVP до состояния, где ссылку можно спокойно дать детям и быстро понять, что пошло не так, если что-то сломается.

## Текущее состояние

Оффлайн-игра работает хорошо. Онлайн-часть уже не черновик: есть Node-сервер, регистрация/логин, серверные профили, сессии, публичные и приватные комнаты, восстановление активной комнаты, завершение партии и реванш.

Локальная подготовка перед деплоем закрыта:

- `npm.cmd run check` проходит;
- `npm.cmd run online-smoke` локально проходит;
- API-ошибки пишутся в `.runtime/server-errors.log`;
- backup `.runtime` автоматизирован;
- восстановление `.runtime` после рестарта Node проверяется отдельным скриптом;
- CSS/структура онлайн-экрана локально просмотрены на явные мобильные проблемы.

## Что уже сделано локально

1. **Логирование ошибок API**

   В `server.js` добавлено логирование ошибок, которые доходят до общего API `catch`.

   Файл:

   ```text
   .runtime/server-errors.log
   ```

   В логе есть дата, HTTP-метод, путь, статус, сообщение ошибки, remote address, user-agent и stack trace для неожиданных ошибок.

2. **Backup `.runtime`**

   Добавлена команда:

   ```bash
   npm.cmd run runtime-backup
   ```

   Она создает zip-архив в `.runtime/backups/` и кладет туда:

   - `profiles.json`;
   - `sessions.json`;
   - `online-rooms.json`;
   - `server-errors.log`.

   Команда проверена: архив создается и читается.

3. **Проверка `.runtime` после рестарта**

   Добавлена команда:

   ```bash
   npm.cmd run runtime-restart-check
   ```

   Она запускает сервер на отдельном локальном порту, регистрирует двух игроков, создает приватную комнату, начинает матч, перезапускает Node и проверяет восстановление комнаты через `/api/online/active`.

   Команда проверена: проходит.

4. **Сетевой smoke/e2e**

   Есть команда:

   ```bash
   npm.cmd run online-smoke
   ```

   Сейчас тест проверяет регистрацию двух игроков, серверные сессии, приватную комнату, вход второго игрока, скрытие приватной комнаты из публичного списка, старт партии, запрет хода вне очереди, корректный ход, восстановление активной комнаты, завершение партии, реванш и выход из комнаты.

   Локально проверено: проходит.

5. **Общая проверка проекта**

   `npm.cmd run check` теперь проверяет синтаксис основных JS-файлов и служебных скриптов:

   - `scripts/online-smoke-check.js`;
   - `scripts/runtime-backup.js`;
   - `scripts/runtime-restart-check.js`.

   Локально проверено: проходит.

## Осталось до закрытого теста

1. **Выбрать и настроить хостинг**

   Минимум для Node-сервера:

   - `NODE_ENV=production`;
   - `HOST=0.0.0.0`;
   - `PORT` из переменной окружения платформы;
   - HTTPS через платформу, reverse proxy или Cloudflare;
   - persistent disk/volume для `.runtime`;
   - автозапуск процесса после рестарта или падения.

   Важно: при `NODE_ENV=production` cookie сессии получает флаг `Secure`, поэтому боевой сайт должен открываться по HTTPS. На локальном HTTP для проверки production-режима лучше не полагаться на авторизацию через cookie.

2. **Проверить persistent `.runtime` уже на хостинге**

   На опубликованном сервере нужно убедиться, что после рестарта не исчезают:

   - `.runtime/profiles.json`;
   - `.runtime/sessions.json`;
   - `.runtime/online-rooms.json`;
   - `.runtime/server-errors.log`.

   Если после рестарта профиль или комната исчезают, значит `.runtime` лежит на временном диске и нужен persistent volume.

3. **Прогнать smoke/e2e против опубликованного сайта**

   После деплоя:

   ```powershell
   $env:TEST_BASE_URL="https://your-domain.example"; npm.cmd run online-smoke
   ```

   После запуска против production в `.runtime/profiles.json` останутся тестовые профили `Smoke A ...` и `Smoke B ...`. Для закрытого теста это терпимо, но перед публичным запуском их лучше удалить или завести отдельное тестовое окружение.

4. **Сделать backup перед тем, как дать ссылку**

   Перед закрытым тестом:

   ```bash
   npm.cmd run runtime-backup
   ```

   Для первого закрытого теста достаточно ручного запуска. Для более широкого доступа лучше настроить регулярный backup persistent volume на хостинге.

5. **Проверить мобильную верстку на реальном устройстве**

   Локально явных проблем не найдено, но после деплоя нужен реальный тест на телефоне:

   - список комнат;
   - создание приватной комнаты;
   - вход по коду и паролю;
   - игровое поле на 32/48/64 карточки;
   - экран результата и реванш;
   - скролл лобби и результата.

6. **Провести закрытый тест на 2-5 человек**

   Дать ссылку нескольким детям/родителям и попросить записывать:

   - устройство и браузер;
   - что нажимали;
   - что ожидали увидеть;
   - что произошло;
   - примерное время ошибки.

## Как сделать деплой почти полностью через Codex

Автодеплой пока не трогаем. Но деплой можно организовать так, чтобы Codex делал не только инструкции, но и большую часть реальных действий.

Нужен один из "мостиков" доступа:

- CLI хостинга, уже авторизованный на этой машине (`railway`, `render`, `fly`, `vercel`, `netlify`, `docker`, `gh` и т.п.);
- GitHub-репозиторий с автодеплоем на хостинг;
- токен/ключ хостинга как переменная окружения;
- подключенный коннектор/инструмент деплоя.

После этого Codex может:

- подготовить конфиги деплоя;
- проверить `start`-команду и env-переменные;
- задать или описать `NODE_ENV=production`, `HOST=0.0.0.0`, `PORT`;
- помочь настроить persistent volume для `.runtime`;
- запустить деплой через CLI/инструмент;
- проверить `/api/health`;
- прогнать `online-smoke` против опубликованного URL;
- обновить чеклист по фактическому результату.

Граница простая: Codex не может сам войти в аккаунт хостинга без доступа, но если доступ уже есть через CLI, GitHub, токен или коннектор, он может вести деплой почти end-to-end.

## Уже не блокер

Реальный ручной тест в двух браузерах/на двух серверах уже проходил нормально, поэтому не держим его как обязательный отдельный пункт перед этим закрытым тестом. Достаточно быстро повторить основной сценарий после деплоя: регистрация, приватная комната, вход второго игрока, несколько ходов, refresh, завершение или реванш.

## Не обязательно до первого закрытого теста

- WebSocket вместо polling.
- SQLite вместо JSON.
- сложный рейтинг/Elo;
- матч-история;
- случайный подбор соперника;
- чат.

## Проверка Firefox и Safari перед более публичным релизом

Перед широкой публичной ссылкой отдельно прогнать acceptance-тесты не только в Chrome/Edge, но и в Firefox/Safari:

- регистрация, вход, выход и повторный вход в профиль;
- открытые комнаты: статус "Свободно / Ждет 1/2 / Идет партия";
- приватные комнаты: создание, код входа, пароль, подключение второго игрока;
- сетевая партия: несколько ходов, задержка отображения хода во втором браузере, завершение;
- реванш: оба порядка нажатия кнопки, повторный клик после старта реванша;
- refresh во время ожидания, во время партии и на экране результата;
- подгонка карточек на всех уровнях и в обоих типах игры;
- мобильная верстка, особенно `100dvh`, высота игрового поля, скролл лобби и результат.

Риски:

- Safari/iOS может иначе вести себя с `100dvh`, cookies/localStorage и private browsing;
- Firefox нужно отдельно проверить на `crypto.subtle`, `AbortController`, `replaceChildren`, `Intl.DisplayNames`;
- старые браузеры не поддерживаются, проект рассчитан на современные версии.
